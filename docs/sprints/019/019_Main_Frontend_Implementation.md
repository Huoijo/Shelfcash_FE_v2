## Architecture and runtime changes

React Router, AuthProvider, StoreProvider, four-layer app/pages/features/shared structure and cookie-backed HTTP remain. Existing workflows retain Import/Planning state, CAS, Review pins and atomic commit semantics. The additive typed API boundary now has React readers/writers used by the new surfaces; no second transport, fabricated session or bearer token was introduced.

- **Account lifecycle:** `/register` calls A02 with email/display_name. `/email-verification` captures and scrubs proof in memory, explicitly submits password with A05, and resends through A06 with the server retry deadline. `/password-reset` calls A07; credential completion remains N7. Verification never accepts an invitation, creates a Store or establishes a session. Explicit login uses A01 → A03; actual accessible Store context routes to the app/zero-Store/invitation. Existing session-error recovery remains usable.
- **Zero-Store:** `/store` keeps the normal existing-Store workspace as default; authenticated accounts with no Store see conditional T03 bootstrap. Supported fields are name/timezone/currency, explicitly entered. Known receipt permits Store refresh/open. Unknown result locks edits/new creation, offers T01 readback and exact-key replay. Empty T01 does not prove noncreation.
- **Notifications:** the shell bell and `/notifications` use NF02/NF01/NF03 for account/Store filters, unread/read, count, pagination, snapshot consistency, detail, ack failure and exact replay. Reading/opening never performs a business decision. Only matching, registered membership/permission-request/mapping-submission paths navigate. Source permissions and lifecycle are rechecked at the destination; null links do not invent a denial cause. Permission requests use PR03 read-only context and can lead an Owner to the existing membership administration surface, with no implicit PR04 approval.
- **Submission lifecycle:** Staff Step 3 reads persisted MQ02 submissions for the current batch, explicitly submits one selected valid Profile via MQ01 with reason and current pins, waits, reads feedback and can resubmit after edits. `/imports/approvals` provides actual queue/filter/paging, pinned MQ03 detail/evidence and N5 decisions. Request changes requires an active Staff membership matching the submitter, current Owner identity distinct from submitter, review eligibility and the published allowed action. Reject remains separate. Owner self-proposal approval remains available. Withdraw reads fresh I04 import revision before MQ01, rather than reusing the captured submission's old import revision.
- **Feedback continuation:** changes_requested opens the retained import directly at Step 3 and selects the submission's known sheet. It preserves source/context and unrelated persisted resolutions. BE does not publish a structured affected resolver/issue target, so the four resolver groups remain explicit user choices; no feedback text is interpreted as a command.
- **Profile evidence:** full spec, first profile, missing fields, warnings and captured evidence remain visible. Changed view uses an M01 baseline only when profile ID and active version match; unavailable baseline is explicitly unknown, never substituted with latest unrelated spec.
- **Review/Commit:** independent persisted Review and Commit acknowledgment/reasons remain. Commit reason is optional for complete pure insert/NO_OP Preview and required for consequential actions/update effects/incomplete row evidence. No Review reason reuse. Existing sales/supplier global blockers remain enforced in navigation and writer guards.
- **Planning:** R01 carries the exact full `planning_request`; returned supplied-request assessment/mode must match. The create gate records that request and refuses same-date changed configuration. Historical Run budget is read from `captured_budget`, including known zero, instead of current Store budget.
- **Today:** D01 now drives supported inventory attention, import/mapping/permission tasks, current readiness and latest Run navigation using the frozen layout. Unknown/partial/forbidden sections remain explicit. Latest Run is not mislabeled a pending procurement decision. Seven-day outlook, arrivals and AI are unavailable without their backend contracts.

Mutation state keeps the exact original key/body/CAS across internal navigation in actor/Store/resource-scoped memory. Current writes notify subscribers; mounted unresolved writers block Store change and warn on reload; original Store/resource intent remains isolated across internal route changes. An exact replay denial cannot clear original uncertainty. Public email configuration failure `EMAIL_DELIVERY_UNAVAILABLE` is a documented definite rejection; other 5xx remain unknown. No automated mutation retries, timer-driven business decisions or optimistic business success.

## Intentional design adaptations

A02 accepts no password; the password is established by A05 (12–128 Unicode code points), unlike the prototype signup form. A05 returns next_action=login and no authenticated account identity; skipping login would reuse an unrelated session. Store type/address have no T03 fields, so the frozen card geometry presents explicit timezone/currency instead. These are contract-backed adaptations, not new persistent business fields.

The inbox supports the three published notification object families. Import/invitation notification examples in the prototype are not fabricated. Permission-request approval/decline-invitation APIs remain callable services until adequate action designs exist. Today uses known D01 sections and retains unavailable frozen sections rather than manufacturing a forecast or procurement state. See [019 integration gaps](../../../FE_ask/019_Freeze_Integration_Gaps.md).
